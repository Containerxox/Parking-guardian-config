# Phase 1 ↔ Phase 2 부하 테스트 계획 (초안, 2026-11-04 — 아직 실행하지 않았다)

**실행 가능한 절차·비용·정리: [loadtest-execution-plan-2026-11-04.md](loadtest-execution-plan-2026-11-04.md), [cost-and-teardown-plan-2026-11-04.md](cost-and-teardown-plan-2026-11-04.md).** 이 문서는 가설과 지표를 담고, 위 문서가 구체화한다.

**이 문서는 계획이다. 부하 테스트를 실행하지 않았고, 아래 시나리오의 결과는 없다.** 표기: **[관찰]** 이 저장소·클러스터·기록에서 직접 읽은 사실, **[계산]** 관찰값으로 계산,
**[추정]** 근거 있는 해석(미확인). Phase 1 측정의 사전 등록 규칙은 앱 리포 `docs/measurements/phase1/README.md`, 도구는 `loadtest/` 이며, 이 계획은 그 틀을 그대로 이어 쓴다
(가설과 통과 기준을 결과를 보기 전에 고정, 불리한 결과도 기록).

## 1. 비교 목적
Phase 1 은 접수 요청 안에서 AI 판정까지 끝내는 **동기식**(ADR 0018), Phase 2 는 접수(202)와 판정을 큐로 떼어 낸 **비동기식**(ADR 0019)이다. 비교하려는 것은 "같은 모델·같은 요청값에서 구조(HTTP 한 번 + 큐 한 번)가 무엇을 바꾸는가"다.

| 가설(안) | 측정 | 성립하지 않으면 |
|---|---|---|
| H1. 과부하에서 Phase 2 는 접수를 거절하지 않고 판정 지연으로 흡수한다(Phase 1 은 503 으로 거절) | 접수 성공률(2xx), 접수 시간, 접수→판정 지연 분포, 큐 길이·가장 오래된 메시지 나이 | 거절이 없던 것은 한도 안이었던 것으로 기록. 큐가 무한정 쌓이면 "거절 대신 무한 대기" 라는 결과로 기록 |
| H2. 사진 부하가 있어도 일반 API p95 는 Phase 1·2 모두 기준(500 ms) 안이다 | 일반 API p95·오류율 | 구조와 무관한 한계(DB·CPU)로 기록 |
| H3. Worker 를 늘리면 처리량이 늘되, **장비 수가 상한**이다(FIFO 그룹 = 장비) | 장비 3대에서 Worker 1→2→3 처리량 | 비례하지 않으면 원인(노드 CPU, DB, 장비별 직렬화) 기록 |
| H4. 큐 기반 확장(KEDA)은 CPU 기반 HPA 보다 늦게 반응한다 | 부하 시작 → Worker 증가 → 지연 회복 시간 | 반응이 더 빠르면 그대로 기록 |
| H5. Worker 장애는 데이터 손실 없이 재처리된다(60초 가시성, 펜싱) | Worker 종료 후 미처리 0·중복 결과 0·복구 시간 | 손실·중복이 있으면 결함으로 기록 |

통과 기준은 Phase 1 과 같은 값(일반 API p95 < 500 ms, 오류율 < 1%)을 쓰고, Phase 2 전용 기준(예: 접수 성공률, 판정 완료율, 큐 회복 시간)은 실행 전에 이 문서에서 고정한다.

| 장비 | Phase 1 은 데모 장비 2·4·5 | **시험 전용 장비 3대를 새로 만든다(회사 3 안, 별도 승인)**; Phase 1 재측정도 같은 장비로 | 데모 데이터 보호, 같은 장비 수. 데모 장비에는 보내지 않는다 |
| 부하 발생 위치 | PC(Wi-Fi) → ALB | 동일 위치 | 네트워크 요인을 같게. ALB 를 쓰려면 DNS 연결([dns-admin-ui-plan.md](dns-admin-ui-plan.md)) 또는 k6 `hosts` 옵션이 필요 |
| 캐시 상태 | 측정 전에 이미지·모델을 모든 노드에 미리 받아 두고(워밍업), 콜드 스타트는 **따로** 측정 | 동일 | 첫 E2E 에서 이미지 pull 이 시간에 21 s 를 더했다([위반 확정 E2E](e2e-aws-violation-confirm-2026-11-04.md)) |

**공존 상태(inference + Worker 동시)의 영향**: CPU 요청 4235m / 5790m(73%)이고 1000m 자리가 노드 하나뿐이라, Worker 가 올라가면 inference 롤링·3번째 inference·Worker 2번째가 못 들어간다([ops-risks-2026-11-04.md R7](ops-risks-2026-11-04.md)).
그래서 Phase 1 측정은 Worker 0 상태에서, Phase 2 측정은 inference 를 제거한 비교 구성에서 **각각 따로** 한다. 공존 부하(두 경로를 동시에)는 별도의 선택 실험이며 노드 +1 이 있어야 의미가 있다.

## 5. 예상 병목 [추정, 실측 전]
1. **장비별 FIFO 직렬화**: 같은 장비의 메시지는 앞 것이 끝나야 다음이 나온다. 장비 3대면 동시 처리는 최대 3(Worker 3), 한 장비로 몰리면 그 장비의 지연은 Worker 를 늘려도 줄지 않는다. Phase 1 은 장비와 무관하게 병렬이므로 **공정성에 영향이 크다** → 같은 장비 수로 맞추고 결과에 이 한계를 적는다.
2. **Worker CPU**: Worker 는 모델 두 개를 프로세스 안에서 돌리고 CPU 약 0.7~1 코어를 쓴다(위반 확정 E2E 에서 최대 710m [관찰]). 노드당 1개가 한계.
3. **KEDA 반응**: 폴링 15 s + HPA 15 s + Worker 시작(캐시 있으면 약 20 s, 없으면 약 45 s [관찰: 두 E2E])이 부하 상승 초반의 지연을 만든다. `min 0` 이면 첫 사진이 콜드 스타트를 치른다.
4. **RDS `db.t4g.micro`(버스트형)**: 지속 부하에서 CPU 크레딧이 줄면 처리량이 꺾일 수 있다 [추정, 실측 필요]. 작업·결과·세션 행이 사진마다 늘어난다.
5. **Relay 1개**: 2초 주기·배치 50 으로 발행한다. 도착률이 매우 높으면 발행 지연이 병목일 수 있다 [추정].
6. **backend 2개(HPA)**: 접수가 사진 저장(S3 PUT)과 DB 기록을 하므로 접수 부하에서 CPU 를 쓴다. 이 노드들은 inference/Worker 와 CPU 를 나눈다(요청 대비 사용은 낮음 [관찰]).
7. **가시성 60 s·재수신 3회**: 처리 지연이 길어지면 메시지가 재전달되어 `maxReceiveCount` 에 닿아 DLQ 로 갈 수 있다 — 과부하에서 데이터 손실처럼 보일 수 있으니 DLQ 건수를 반드시 함께 본다.

## 6. 비용과 노드 확장 필요 여부
- 현재 시간당 약 **$0.60**(RDS·ALB 포함) [계산: 이전 보고의 추정 합]. 세션 6시간이면 약 $3.6.
- **비교 구성 + Worker 3개는 노드 증설 없이 들어간다**(1000m 자리 3개: 노드별 여유 1190/1275/1090m [계산]), 다만 배포 Job 은 Worker 2 이하에서만.
- 공존 상태의 동시 비교, inference 3번째 Pod, Worker 4개 이상은 **노드 +1** 이 필요하다: 약 +$0.12/h(단가 확인값 $0.11771/h), 새 노드는 이미지 캐시가 없어 첫 기동에 pull 시간이 든다.
- NAT 데이터·SQS·S3 요청은 소액 [추정]. 부하 발생 위치가 PC 면 ALB 비용(LCU)도 소액.
- RDS: 20 GB 로 충분하나, 사진 수만 건 × 3행씩 쌓이는 것을 시험 뒤 정리 방침(삭제하지 않는 규칙과 충돌)과 함께 정해야 한다.

## 7. 공정한 비교를 위한 규칙
1. 가설·통과 기준·무효 조건을 **실행 전에 고정**하고 변경 기록을 남긴다(Phase 1 방식). 결과를 본 뒤 바꾼 것은 그렇다고 적는다.
2. 같은 날 같은 클러스터에서 Phase 1 재측정과 Phase 2 측정을 번갈아 하거나 연달아 하여 환경 편차를 줄인다. 같은 빌드, 같은 사진, 같은 장비 수, 같은 도착률 프로필.
3. 콜드 스타트(이미지·모델)와 정상 상태 지연을 **분리**해 보고한다(워밍업 후 측정 + 별도 콜드 시나리오).
4. 구조적으로 다른 지표(접수 응답 시간 vs 판정까지의 응답 시간)는 단독 비교하지 않고 접수→판정 지연으로 맞춘다.
5. 단일 실행 값을 일반 성능으로 쓰지 않는다. 반복 3회의 범위와 무효 회차를 함께 적고, 실측과 추정을 구분한다.
6. 불리한 결과(큐 적체, 지연 증가, DLQ)도 숨기지 않는다.

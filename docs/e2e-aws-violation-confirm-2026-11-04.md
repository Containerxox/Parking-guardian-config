# Phase 2 위반 2회 확정 + 관리자 알림 E2E (AWS, 2026-11-04)

**이 문서의 수치는 사진 2장, 1회 실행의 관찰값이다.** 평균·분포·처리량이 아니며 다른 환경·부하에 그대로 쓰면 안 된다. 표기: **[실측]** DB·S3·로그·쿠버네티스 기록에서 읽은 값,
**[계산]** 실측값으로 계산한 값, **[추정]** 근거가 있는 해석이지만 확인하지 않은 것. 앞선 [빈 공간 사진 E2E](e2e-aws-first-run-2026-11-04.md)와의 비교는 맨 아래 표를 먼저 읽는다
(이미지 캐시 상태와 사진 내용이 달라 시간을 그대로 비교할 수 없다).

## 범위와 환경
- 확인한 것: 접수 202 → 첫 판정 `violation`(= `violation_pending`) → 확인 명령(`capture_confirm`) 생성·하트비트 전달 → `due_at` 이후 확인 사진 → 두 번째 판정 `violation` → **위반 확정**
  → S3 증거 사진 → 시험 관리자 IN_APP·EMAIL 알림 → 이력 → 확인 명령 이행 → KEDA 0→1→0 → Worker 정상 종료 → Argo CD 상태 유지 → 기존 데이터 변경 없음.
- 환경: EKS 1.35, 노드 3대(`m7i-flex.large`), Phase 1·2 공존 구성(backend 2, inference 2, frontend, relay; Worker min 0 / max 1), 이미지 태그 `60c2e43`.
  CloudWatch Agent CPU 요청 100m, `worker` 는 `replicas: 0` 으로 태어나고 Application 이 `/spec/replicas` 를 무시한다([phase2.md 8.8](phase2.md)).
- 대상: **전용 시험 환경만** — 회사 `E2E-TEST-COMPANY`(id 3), 주차장 `E2E-TEST-LOT`(id 6), 장비 `RPI-E2E-TEST-01`(id 6), 시험 관리자(id 6, 주차장에 배정). 데모 장비는 건드리지 않았다.
- 입력: `sample_b.jpg`(차량 사진, 336,086 바이트)를 두 번 보냈다. 요청은 backend Pod 안에서 `127.0.0.1` 로 보냈다(ALB·DNS 를 거치지 않았다).
- 실행: 사용자가 본인 터미널에서 해시 검증된 스크립트로 실행(장비 키는 `rotate-key` 로 받아 메모리에서만 사용·출력 없음). 제가 한 일은 읽기 전용 사전 점검·관측·사후 검증이다.
  **사용자 터미널에 찍힌 스크립트 출력은 전달받지 못했다.** 아래 값은 모두 서버 기록과 관측 파일에서 독립적으로 읽은 것이고, 클라이언트 측 API 응답 시간은 이 실행에서 측정값이 없다.

## 자원 [실측, 10초 간격 표본]
- Worker 컨테이너: CPU 최대 **710m**(표본 12개), 메모리 최대 **891Mi**(요청 1000m / 1.5Gi). `kubectl top` 은 표본이라 실제 순간 최대가 아닐 수 있다.
- CloudWatch Agent: CPU 최대 40m. 로그·지표 수집은 시험 중에도 계속됐다(최근 3분 이벤트가 4개 로그 그룹 모두에서 확인됨).
- 노드: 시험 중 Pending·재시작·다른 Pod 문제 없음.

## Argo CD 와 `ignoreDifferences` [실측]
Worker 가 1개로 올라온 약 5분(07:06~07:11) 동안 타임라인의 Argo 열이 계속 `Synced/Healthy` 였고, `parking-guardian` 의 마지막 Sync 는 04:48:15 그대로였다.
즉 `worker` 의 `/spec/replicas` 가 Git(0)과 달라도 Argo CD 가 되돌리지 않았다. 이 구성의 **첫 실제 확인**이다([phase2.md 8.8](phase2.md)).

## 기존 데이터 보호 [실측]
시험 직전에 찍은 기준선과 비교했다(시험 장비 행은 제외, 나머지 기존 행은 해시로 비교). 15개 테이블 모두 기존 행이 같다.
새로 늘어난 것: 위반 +1, 알림 +2, 이력 +2, 감사 +1(`MACHINE_KEY_ROTATED`), 작업 +2, 결과 +2, 세션 +1, 확인 명령 +1, 로그인 세션 +1. 회사·주차장·장비·관리자·배정은 +0.
다른 회사의 위반 4건·알림 8건도 그대로다. 시험 데이터(위반·알림·이력·증거 사진)는 검증 결과로 유지했고 삭제하지 않았다.

## 앞선 빈 공간 사진 E2E 와의 비교 (같은 조건이 아니다)
| | 첫 E2E (05:16) | 이번 E2E (07:06) |
|---|---|---|
| 입력 | 빈 공간 사진 1장 `sample_f`(9.6 MB) → `no_vehicle` | 차량 사진 2장 `sample_b`(336 KB) → `violation` ×2 |
| **이미지 캐시** | **Worker 이미지·aws-cli 이미지 모두 노드에 없었음**: pull 15.8 s + 5.4 s | **두 이미지 모두 노드에 이미 있음**(`already present`): pull 0 s |
| 접수 → 첫 판정 | 44.8 s | 24.7 s |
| KEDA 반응 | 발행 후 약 1 s | 발행 후 약 7.5 s |
| 모델 다운로드 | 4 s | 4 s |
| 모델 로딩 / preload | 6.1 s / 7.25 s | 5.2 s / 6.31 s |
| 추론 | 408 ms(빈 사진) | 715 ms / 688 ms(차량) |

- **첫 E2E 의 44.8 s 에는 이미지 pull 약 21 s 가 들어 있고 이번 24.7 s 에는 없다.** 두 값의 차이를 성능 개선이라고 읽으면 안 된다.
- KEDA 반응 시간은 폴링 주기(15초) 안의 우연한 위치에 좌우된다. 두 번의 1 s 와 7.5 s 는 각각 한 번의 관찰이다.
- 추론 시간은 사진 내용·크기에 따라 다르다(빈 공간 9.6 MB 와 차량 336 KB). 서로 비교하지 않는다.

## 이 결과로 말할 수 없는 것
- 처리량, 지연 분포, 동시 접수, Worker 2개 이상의 확장, 장비 여러 대의 FIFO 병렬성, 부하 아래의 KEDA 반응.
- 오류 경로: DLQ·재전달·Worker 장애·DB 장애·비밀번호 회전 중의 동작(이 실행에서는 일어나지 않았다).
- 실제 메일 발송(console 백엔드), 관리자 UI 로그인·알림 조회 화면, ALB 경유 접수, DNS 연결(→ [dns-admin-ui-plan.md](dns-admin-ui-plan.md)).
- 이미지 캐시가 없는 새 노드에서의 위반 확정 지연(첫 E2E 의 pull 시간을 더해 볼 수는 있으나 이번 흐름에서 측정하지 않았다).

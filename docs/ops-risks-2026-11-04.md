## R3 — Worker·Relay 프로세스가 멈췄는데 컨테이너는 살아 있는 경우

| 항목 | 내용 |
|---|---|
| 현재 상태 | `worker`·`relay` Deployment 에 **livenessProbe·readinessProbe·startupProbe 가 없다** [관찰: 배포된 매니페스트]. 종료 유예는 worker 60 s, relay 15 s. |
| 코드 방어 | SQS 클라이언트에 연결 5 s·읽기 30 s 제한(긴 폴링 20 s + 10 s) [관찰: `adapters/queue.py`]. 작업 임대(lease) 55 s < 가시성 60 s, `claim_attempt` 펜싱 [관찰]. |
| **코드에 없는 것** | DB `statement_timeout`·`lock_timeout`·연결 제한이 없다(검색에서 해당 설정 0건). SQLAlchemy 엔진 옵션은 `pool_pre_ping` 하나뿐 [관찰: `config.py`]. 그래서 DB 쿼리가 무한 대기하면 예외가 나지 않고 루프가 멈춘다 [추정: 코드상 가능한 경로이며 재현하지 않았다]. |
| 발생 조건 | DB 락·네트워크 소켓 무응답, 교착, 모델 추론 중 무한 루프 등으로 `run_loop` 가 한 바퀴를 못 돈다. 프로세스는 살아 있다. |
| 영향 | **Kubernetes 는 감지하지 못하고 Pod 를 되살리지 않는다.** KEDA 는 큐 길이만 보고(max 1 이라) 새 Pod 를 만들지도 못한다. 큐에 메시지가 쌓이고 판정이 멈춘다. 접수 API 는 계속 202 를 준다(조용한 정지). 이미 가져간 메시지는 60 s 뒤 큐에 돌아오지만 받을 Worker 가 없다. 수신 횟수는 받아야 늘어나므로 DLQ 로도 가지 않는다 [계산]. 4일 보존(345,600 s)이 지나면 Relay 복구가 되살린다(설계). |
| 재현 방법 | AWS 에서는 장애 주입이라 하지 않았다. **로컬(Compose)**: Worker 프로세스에 `kill -STOP`(정지)을 보내거나, 다른 세션에서 해당 작업 행에 `SELECT … FOR UPDATE` 로 락을 잡아 claim UPDATE 를 막는다. 기대: 컨테이너는 Running, 메시지 처리 중단, `ApproximateAgeOfOldestMessage` 증가. |
| 개선안 | ① **heartbeat 파일 + exec livenessProbe**: 루프를 한 바퀴 돌 때마다 `/tmp/alive` 를 갱신, probe 는 `test $(( $(date +%s) - $(stat -c %Y /tmp/alive) )) -lt 120`. 한 바퀴는 긴 폴링 20 s 또는 처리 중 ≤ lease 55 s 라 임계 120 s 는 오탐을 피한다. preload(약 7~10 s, 첫 E2E 에서 컨테이너 시작 → 준비 약 9 s)는 `startupProbe`(또는 `initialDelaySeconds: 90`)로 덮는다. 앱 변경 약 15줄 + 테스트(Worker·Relay). ② **DB 제한**: 연결 옵션 `statement_timeout`(예 30 s)·`lock_timeout` 으로 DB 무한 대기를 예외로 바꾼다(앱 설정 변경). ③ **SQS `ApproximateAgeOfOldestMessage` 경보**(예: 300 s 초과가 2번 연속): 정지를 알려 주지만 되살리지는 않는다. ①과 함께 쓴다(Terraform data/cluster 스택 추가, 경보 1개 [추정: 무료 한도 10개 안]). |
| 부작용·위험 | ① 재시작은 처리 중이던 작업을 끊는다 → 60 s 뒤 재전달·펜싱으로 안전하다(설계 [관찰]). CPU 가 극도로 부족해 루프가 120 s 넘게 못 돌면 오탐 재시작이 반복될 수 있다(R7 과 연결) → 임계·`failureThreshold` 를 보수적으로. exec probe 는 `sh`·`stat` 이 이미지에 있어야 한다 [추정: 슬림 이미지 확인 필요]. |
| 검증 기준 | (a) 로컬 정지 시험: 정지 후 **150 s 안에** 컨테이너가 재시작되고, 큐의 메시지가 새 프로세스에서 처리된다. (b) 정상 E2E·preload·55 s 처리 중에는 재시작 0. (c) Worker 0↔1 전환에서 probe 오탐 0. (d) 경보는 큐 정체 시에만 울린다. |

## R6 — RDS 관리형 비밀번호 회전과 오래 사는 Pod

**현재 흐름 [관찰]**: Secrets Manager(RDS 관리형, 회전 켜짐, 마지막 회전 11-04 04:23 UTC·다음 11-11 23:59 UTC) → External Secrets Operator(`refreshInterval: 1h`, Pod Identity 로 4개 시크릿 읽기)
→ Kubernetes Secret(`backend-secrets`, `pipeline-secrets`; ExternalSecret 이 소유) → `envFrom` → **Pod 환경변수(컨테이너 시작 때 고정)**.

| 항목 | 내용 |
|---|---|
| 발생 조건 | 회전이 일어나면 DB 의 비밀번호가 즉시 바뀐다. 이후 ① ESO 가 갱신하기 전(최대 1h)에는 Secret 이 옛 값, ② 갱신 뒤에도 **떠 있는 Pod 의 환경변수는 옛 값**이다. |
| 영향 [관찰: 11-04 실제 발생] | Argo 가 sync 마다 새로 만드는 마이그레이션 Job 이 옛 비밀번호로 `password authentication failed` → `parking-guardian` 앱 `Degraded`·sync 중단. backend·relay 는 열린 연결 덕에 즉시 실패하지 않았지만, **새 연결이 필요해지는 순간(연결 재생성, Pod 재시작, 노드 교체) 실패한다** [추정: PostgreSQL 은 기존 세션을 끊지 않음]. Worker 는 0→1 때마다 시작하므로 Secret 이 갱신돼 있으면 새 값을 받는다(자연 복구되는 유일한 워크로드). |
| 재현 방법 | AWS 에서 임의 회전은 RDS 비밀번호 변경이라 하지 않았다. 로컬(Compose): Postgres 역할 비밀번호를 바꾸고 backend 를 두고 새 연결 실패를 본다. 또는 승인된 시험 창에서 `rotate-secret` 한 번(별도 승인). |
| 현재 대응 | [runbook-rds-rotation.md](runbook-rds-rotation.md): 회전 확인 → `force-sync` → 새 연결 확인 → relay → backend 롤링 재시작. 한계: **사람이 해야 하고**, 잊으면 장애, 회전 시각을 모르면 발견이 늦다(이번에도 마이그레이션 실패로 알게 됨). |

**해결안 비교**

| 방안 | 동작 | 추가 구성·비용 | 위험·한계 |
|---|---|---|---|
| A. 런북(현재) | 사람이 갱신·재시작 | 0 | 누락 가능. 실험 기간(회전 주 1회)에는 최소 해결안 |
| B. **Reloader** + `refreshInterval` 단축 | Secret 변경을 보고 지정한 Deployment 를 롤링 재시작 | Pod 1개. 차트를 렌더링해 보니 replicas 1, **리소스 요청 없음(BestEffort)** [관찰] → 실제로 쓸 때 약 10m/50Mi 를 지정(값은 [추정]). ESO 갱신 5분으로 줄이면 GetSecretValue 가 월 약 2.6만 건 이상 [계산, 시크릿 3개 읽기면 더 많음], 요금은 소액 [추정: 공시 단가 기준 월 $1 미만] | ClusterRole 이 **Secret·ConfigMap 을 읽고 Deployment 를 patch** 한다 [관찰: 렌더링] → `watchGlobally` 를 끄고 네임스페이스로 제한 검토. 롤링은 CPU 가 필요(R7: backend surge 200m, relay 50m 은 들어감, worker 는 `maxSurge 0`). Argo 는 파드 템플릿의 추가 어노테이션을 되돌리지 않았다(`kubectl rollout restart` 로 확인한 사례 [관찰]) — Reloader 방식은 [미확인]. 마이그레이션 Job 은 여전히 ESO 갱신 주기만큼 늦을 수 있다 |
| C. 앱이 비밀을 동적으로 읽음 | 파일 마운트 + 인증 실패 시 재조회·재연결 | 앱 코드 변경 + 테스트 | 가장 정확하고 가장 큼 |
| D. RDS IAM 인증 | 15분 토큰으로 접속 | Terraform·앱 모두 큼 | 설계 변경. 지금은 과함 |
| E. 회전 주기 연장·중지 | 문제 발생 빈도를 줄임 | Terraform data 스택 변경(별도 승인) | 보안 자세를 낮춘다. 부하 테스트 기간 한정이면 고려 가능 |

- **권고**: 부하 테스트 전에는 A 를 유지하되 다음 회전 시각(11-11 23:59 UTC)을 시험 창과 겹치지 않게 확인한다. 상시 운영이라면 B(+갱신 주기 단축)가 비용 대비 가장 작은 자동화다. C 는 장기 과제.
- **검증 기준(B 도입 시)**: 승인된 시험 창에서 ExternalSecret 강제 갱신 후 대상 Pod 만 롤링 재시작되고(그 사이 `/readyz` 오류 0, 중단 요청 0), 새 Pod 의 `select 1` 성공, Argo 가 `Synced` 유지, Reloader 가 비대상 워크로드를 건드리지 않는다.

## Fluent Bit `cloudwatch-agent.amazon-cloudwatch:4311` 경고

| 항목 | 내용 |
|---|---|
| 현상 [관찰] | 3개 Fluent Bit Pod 모두에서 1분마다 `getaddrinfo(host='cloudwatch-agent.amazon-cloudwatch', err=-2) Name or service not known` + `[kubernetes] no upstream connections available to cloudwatch-agent.amazon-cloudwatch:4311`. 최근 400줄 중 약 141줄(≈ 1분에 2줄 × Pod). |
| 설정 [관찰] | `fluent-bit-config` 의 application 로그 `[FILTER] kubernetes` 에 `Use_Pod_Association On`, 앞선 `[FILTER] aws` 에 `Enable_Entity true`. 설정 파일에는 4311 이 직접 적혀 있지 않다(기본값을 쓴다). |
| 4311 의 용도 | Fluent Bit 문서: 이 기능은 **로컬 CloudWatch Agent 에서 pod → 서비스·환경 매핑**을 가져와 로그에 서비스 맥락(Application Signals·entity)을 붙인다. 기본 접속 대상이 정확히 `cloudwatch-agent.amazon-cloudwatch` : `4311`, 갱신 60 s [출처: docs.fluentbit.io Kubernetes 필터]. 경고가 1분마다 나오는 것과 맞는다. |
| 서비스 상태 [관찰] | `amazon-cloudwatch` 에 **Linux 용 `cloudwatch-agent` Service 가 없다**. 있는 것은 `cloudwatch-agent-monitoring`(8888)과 Windows 용(4311 포트가 있지만 endpoint 가 없음). Linux DaemonSet 컨테이너는 포트를 선언하지 않았다. 그래서 이름이 풀리지 않는다. |
| 원인(해석) [추정] | 이 클러스터는 애드온 설정에서 Application Signals 를 껐다(`applicationSignals.enabled=false`, 자동 계측 init 컨테이너를 피하려고). 그러면 에이전트가 pod 매핑 서버·Service 를 만들지 않는데, 애드온의 Fluent Bit 기본 설정은 매핑 조회를 계속 시도한다. 시험 시점의 설정과 일치하지만 **변경 전 로그가 없어(Fluent Bit Pod 가 교체됨) 언제부터인지는 확인하지 못했다.** CPU 요청 변경 때문이라는 근거는 없다. |
| 실제 영향 [관찰] | 로그·지표 수집은 정상이다: 4개 로그 그룹 모두 최근 3분 이벤트 수신, 노드 지표 데이터포인트 정상, E2E 시간대의 `judge-worker` 로그가 application 로그 그룹에 도착. 빠지는 것은 **서비스·환경(entity) 연결 정보**뿐이다 [추정: 이 프로젝트는 Application Signals 를 쓰지 않는다]. |
| 개선 필요성 | **단순 경고에 가깝다. 조치하지 않는 것을 권고한다.** 소음 줄이기 방법은 ① 애드온 `containerLogs.fluentBit.config` 로 Fluent Bit 설정을 통째로 덮어쓰기(스키마에 간단한 끄기 옵션은 없음 [관찰: v6.7.0 스키마]) — 유지 부담이 커서 비권장, ② Application Signals 켜기 — Phase 1 에서 Pod 시작 시간을 흐리고 비용이 붙어 기각한 선택. 바꾼다면 검증은 "경고가 사라지고 로그 그룹 4개의 수신이 그대로인지". |

**Worker 정지·SQS 정체를 지금 감지할 수 있는가 [관찰]**
- 있는 것: SQS 의 CloudWatch 지표(메시지 수, `ApproximateAgeOfOldestMessage`)는 자동 수집됨. `kubectl get scaledobject` 의 READY/ACTIVE. DB 에서 미완료 작업 나이를 직접 조회할 수 있음. AWS 예산 이메일 알림(비용만).
- **없는 것**: CloudWatch 경보 0개, SNS 주제 0개(Terraform 검색 결과 `aws_cloudwatch_metric_alarm`·`aws_sns*` 없음). Worker·Relay 에 프로브 없음, 앱 지표 없음(`app/metrics.py` 는 HTTP·inference 지표만). KEDA 는 정지된 Worker 를 되살리지 못한다.
- 결론: **사람이 지켜보는 시험에는 관찰자로 충분하지만, 사람이 없을 때(밤샘·상시 운영)에는 불충분하다.** 시험 후 순서 제안: ①SQS `ApproximateAgeOfOldestMessage` 경보 + SNS 이메일(Terraform data 스택, 경보 1~2개로 무료 한도 안 [추정]) ②Worker·Relay heartbeat 파일 + exec livenessProbe(R3 개선안 ①) ③DB `statement_timeout`·`lock_timeout`(개선안 ②).

**시험 이후로 미룰 수 있는 것**: R3 프로브·DB 타임아웃, R6 Reloader(B), R7 노드 +1 상시화 여부, Fluent Bit 설정.
